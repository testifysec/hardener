Continuous Confinement

Generating, verifying, and attesting SELinux policy for legacy and vendor software in the DevSecOps pipeline
TestifySec, Inc. · Prepared for Department of Defense software factory and platform teams
Abstract Confinement policy should be a build artifact the pipeline proves, not a configuration the program hopes for. DoD systems on Red Hat Enterprise Linux must run SELinux in enforcing mode, but much of the software on those systems ships with no SELinux policy: commercial packages, contractor deliverables, legacy applications that predate the mandate. That software runs unconfined. Operators know the standard workaround, and it is the wrong one: they weaken enforcement for exactly the software they understand least. This paper describes a pipeline that closes the gap. For each application version entering a software factory, the pipeline derives a least-privilege SELinux policy from static analysis and observed runtime behavior, verifies the confined application against its own workload with enforcement active, and packages the policy with a signed verification attestation. The factory gates deployment on that attestation. We tested a reference implementation against thirteen applications, open source and proprietary. All thirteen passed verification. This paper reports those results, the failure classes the automation must diagnose, integration with DoD DevSecOps reference architectures including air-gapped operation, and the limits of behavior-derived policy.

1Problem: the software the mandate forgot

SELinux type enforcement provides the primary mandatory access control on the operating systems that run most DoD ground infrastructure. The Security Technical Implementation Guides require SELinux enabled and enforcing with the targeted policy. The targeted policy confines the distribution's own services and nothing else. It has never heard of the vendor daemon your program depends on. That software receives no domain of its own and runs in a context enforcement barely constrains. The system passes the check. The least understood software on it escapes the control.

Field practice makes this worse. When an unconfined application fails under enforcement, denials arrive faster than the expertise to read them. Too many programs record one of three fixes: setenforce 0, a permissive domain, or a policy a contractor wrote once and no one has touched since. Each one is a standing accreditation finding. The last one also rots, because the vendor changes the application's behavior in version N+1 and the policy still describes version N.

The tooling gap is specific. The ecosystem provides primitives: sepolicy generate builds policy skeletons, audit2allow turns denials into allow rules, restorecon repairs labels. Nothing connects them. audit2allow causes the most damage. It converts every denial into an allow rule, including denials whose correct fix is a label change, and it grants domains access to broad shared types that open other applications' files. Red Hat's own documentation warns against using it blindly. Programs need a repeatable process with a verifiable outcome. No primitive delivers that.

2Approach: confinement policy as a build artifact

The proposition is architectural. The pipeline that builds the application artifact should also produce, test, and version its confinement policy. Derive the policy mechanically. Verify it against the running workload. Ship it with the software it confines. The reference implementation, Hardener, executes this in seven stages (Figure 1).

2.1 Refinement is classification, not translation

Refinement separates this approach from audit2allow. The pipeline classifies each observed denial before it writes any rule:

  • Labeling drift. A denial whose target path falls under the module's own file-context claims but carries a generic label is a labeling problem. restorecon fixes it. An allow rule here would grant the domain access to every file on the system carrying that generic type.
  • Genuine missing permission. A denial against a foreign type with no path claim becomes a candidate allow rule. The pipeline unions permissions across observations and expands helper-execution grants to the complete canonical set, which avoids one-permission-per-round convergence.
  • Privileged access requiring review. Privileged capabilities (sys_admin, setuid, dac_override, …), sensitive targets (shadow_t, selinux_config_t), and broad shared types (var_log_t, tmp_t) never receive silent grants. The pipeline routes them to a human review gate. In CI this is an approval step, and the attestation records the approver's decision.

2.2 Verification is adversarial

Build the verification so that a policy which fails to confine cannot pass. We learned this on the corpus. The worst failure we hit was a mislabeled entrypoint that blocked the domain transition entirely: the service ran unconfined and produced zero denials in its own domain. A naive tool reports that as a perfect run. A passing verdict therefore requires all of the following:

  • the application's workload scenarios succeed with the machine and the domain enforcing. The exercise makes live protocol round-trips and health checks rather than checking that a process exists;
  • the running process provably occupies the generated domain (ps -o label= on the service's main PID);
  • zero residual denials in the verification window, after a bounded re-refinement pass for nondeterministic late paths;
  • static least-privilege assertions hold against the loaded policy via sesearch: no shadow_t access, no etc_t write, no sys_admin or module loading — with consciously accepted exceptions reported by name in the verdict rather than hidden in either direction.

2.3 Static analysis audits dynamic coverage

Policy derived from behavior covers only the behavior you drove. The pipeline does not pretend otherwise. It runs both analyses and reports the difference. Dynamic observation under-approximates: it proves only what the workload exercised. Static import analysis over-approximates: linking setuid() is not calling it. Imported symbols predict policy-relevant behavior such as network binding, privilege dropping, and subprocess execution. The pipeline reports any prediction with no matching grant in the final policy as a coverage gap, meaning capability the binary has that the test workload never drove. On the corpus, this cross-check predicted from the binary alone the exact privilege-drop capabilities that runtime observation later confirmed. Import analysis has nothing to say about statically linked binaries and script entrypoints, and the report states that instead of guessing. Syscall-site disassembly extends coverage to that class in future work.

3The CI integration: continuous confinement

We package the pipeline as a factory stage, not an administrator tool, because the problem is continuous. Vendor software changes. Policy written once is policy rotting. The integration has five elements.

3.1 Placement in the software factory

Hardener executes as a pipeline stage alongside existing SAST, SCA, and container-scanning stages, at the point where a third-party or legacy artifact is admitted to the factory's artifact repository (Figure 2). The stage requires one input beyond the artifact itself: a workload manifest, a declarative description of how to install, start, exercise, and stop the application. The manifest captures the program's operational knowledge about the application. The factory versions it and reuses it on every vendor release that follows.

3.2 The attestation

Every run emits a signed in-toto attestation binding the application artifact and the generated policy package (by digest) to the verification outcome. The predicate carries the security profile (the policy-neutral record of observed least privilege), the verdict and each verification gate's result, every review-flagged rule with its disposition and approver, detected coverage gaps, and the verifier environment — distribution, SELinux policy version, and kernel. The factory stores attestations in Archivista, and consumers verify them offline against the factory's trust root. That matters in disconnected enclaves. The claim a consumer can check is precise: this exact artifact, confined by this exact policy, ran its workload under enforcement with these results, and a named approver accepted every deviation from least privilege.

plex: static cross-check — 6/6 predicted behaviors observed · coverage gaps 0
plex: ✔ PASS → plex-selinux-1.0.0.rpm · in-toto attestation signed and stored
Figure 3. Reference-implementation output for a proprietary media server, verbatim from corpus testing. The flagged rules (executable content written to /tmp) were surfaced for analyst review.

3.3 Attestation-gated deployment

The consuming side closes the loop. Before an application installs in a target enclave, the release process verifies the attestation chain. This applies whether release happens by package promotion, image build, or node configuration management. A verification failure, a missing attestation, or an unapproved flagged rule stops the deployment the same way a failed signature would. Confinement stops being a host hardening aspiration and becomes a supply chain invariant: software does not reach an operational system until its confinement has been proven against its own workload.

3.4 Vendor updates and behavioral drift

When the vendor ships version N+1, the factory re-runs the stage with the same workload manifest. Both outcomes serve the program. If behavior is unchanged, the policy re-verifies and the new artifact gets a fresh attestation with no human effort. If behavior changed, the profile diff is intelligence. A new outbound connection appearing between two versions of a closed-source product is the change a program should examine before fielding. Maybe the vendor added a feature. Maybe they added telemetry. Maybe someone compromised the release. Continuous confinement doubles as behavioral change detection for third-party software, applied at the one point where the program can still say no.

3.5 Disconnected and classified operation

The verifier is a VM recipe and a single static binary; the pipeline has no external dependencies at run time. Factories operating inside accreditation boundaries run the stage on internal KVM-capable runners, and attestation verification requires only the trust root, not connectivity. Artifacts never leave the boundary for analysis.

3.6 One pipeline, three supply-chain contracts

Supply-chain guidance sorts software by origin: first party, the program's own code; second party, contractor and partner deliverables; third party, commercial and open-source artifacts. The confinement stage applies a different contract to each. The observation machinery stays the same. The meaning of a deviation changes.

Third-party software has no counterparty to hold to a claim. The workload manifest is the program's own statement of expected behavior, and observation is discovery. The sections above describe this default.

Second-party software comes with leverage. The contract can require the supplier to deliver a privilege declaration with the artifact: the capabilities, ports, and system access their software needs. The stage verifies observed behavior against that declaration in both directions. Behavior the supplier never declared fails the run, because it signals noncompliance or compromise, and the factory must not grant it quietly. Declared behavior the workload never exercised surfaces as a coverage gap worth closing. Delivery acceptance becomes a checkable contract. In reference-implementation testing, a broker delivered with a declaration that omitted its setuid/setgid privilege drop failed conformance with both capabilities named; the corrected declaration passed.

First-party software carries its declaration in its own repository: a privilege baseline committed next to the code, regenerated only by deliberate review. The stage compares each build's observed behavior against the baseline and fails on drift. A developer whose change binds a new port sees the build fail until someone reviews the new privilege and updates the baseline — snapshot-test semantics for privilege. In reference-implementation testing, adding one listener to a web server's configuration failed the next run with the new port class named (port-bind unreserved_port_t); accepting it was an explicit, flagged, reviewable action that rewrote the committed baseline.

The attestation carries the party class and the conformance outcome, so a consumer can distinguish "observed and granted" from "observed, declared, and verified conformant."

4Empirical results: a thirteen-application corpus

We exercised the reference implementation against thirteen freely obtainable applications chosen to span input forms and licensing, including four proprietary products. The verifier baseline was AlmaLinux 9.8: aarch64, targeted policy, enforcing. The distribution's policy confines none of the thirteen. All thirteen passed. One, webmin, passed with a named and consciously accepted exception. It performs its own authentication against /etc/shadow. That is a true privilege, and the verdict reports it rather than concealing it.

4.1 Failure classes automation must diagnose

Six of thirteen artifacts failed on the first attempt, for six distinct causes. None was a missing allow rule. The tool now detects and names each one. Together they form a working taxonomy of why naive policy generation fails against real vendor software:

  • Symlinked entrypoints (nats-server): the resolved inode's label decides the domain transition. Label the symlink and the service runs unconfined while appearing healthy.
  • Mislabeled entrypoints (Emby): the service can never start, yet it produces zero denials in its own domain. Only watching denials against the module's types from every source domain catches this.
  • NoNewPrivileges=yes units (Splunk): the kernel then permits only bounded transitions, which no generated domain satisfies. The remediation is a unit drop-in, not policy, and the tool says so.
  • Base-policy path collisions (webmin): when a module re-declares a path the distribution already claims, semodule rejects the whole module. The tool detects the collision, defers the claim, and tells the operator.
  • Interpreter ExecStart (Plex): vendor units run ExecStart=/bin/sh -c '…'. Never label the shell as the application's entrypoint. Doing so routes every shell invocation on the system into the application's domain.
  • Application faults misattributed to policy: a workload that fails in a permissive domain with zero denials does not have a policy problem. The tool reports that directly instead of burning refinement rounds and reporting a misleading failure.

The corpus also demonstrated an analytic byproduct. The review gate caught one proprietary product writing executable content into /tmp and running it. An accreditor would want that documented regardless of the confinement outcome.

5Alignment with DoD policy drivers

  • STIG compliance with substance. The RHEL STIGs require SELinux enforcing with the targeted policy. Continuous confinement extends that requirement's practical effect to the third-party software the targeted policy cannot see. It replaces the standing workaround, weakened enforcement, with evidence.
  • RMF and continuous ATO. Per-artifact, per-version attestations form a continuous evidence stream for the access enforcement, least privilege, and least functionality control families (NIST SP 800-53 AC-3, AC-6, CM-7, SC-39). Machine-checkable claims regenerate on every release and replace point-in-time accreditation artifacts.
  • Zero trust. Process-level mandatory access control complements network zero trust from the workload side. The kernel grants the application exactly the observed, reviewed privilege set and denies everything else. That holds on the day an attacker asks the application to do something it has never done before.
  • Software supply chain integrity. The attestation model follows the in-toto pattern DoD software factory guidance already adopts. Confinement evidence rides the same rails as provenance and build evidence. The version-to-version profile diff adds behavioral monitoring of third-party releases.

6Limitations

Stated plainly, because they bound what the attestation claims.

  • Coverage is bounded by the workload manifest. Behavior the manifest never drives never reaches the policy: rare error paths, upgrade and restore procedures, seasonal jobs. The static cross-check narrows this gap and reports it. It does not close it. Treat manifest quality the way you treat test quality, and where risk warrants, run new policies permissive with alerting before promotion.
  • Static prediction has blind spots. Import analysis yields nothing for statically linked binaries and script entrypoints. The report declares this instead of faking confidence. Syscall-site disassembly is planned for the statically linked class.
  • Nondeterminism requires bounded iteration. Some applications exercise new paths only under enforcement or over time. The enforce-phase re-refinement is bounded and progress-gated, and the report shows residual risk as late-round grants.
  • The verifier must match the target. Policy verified on one distribution and policy version is attested for that baseline. A verifier matrix across accredited baselines is roadmap, not current fact.
  • Scope is type-enforcement confinement. The approach generates per-application TE policy on the targeted model. It does not address MLS/MCS category schemes, and it does not replace application-level access control.
  • Accepted exceptions are exceptions. Where an application genuinely requires privileged access, as webmin's shadow authentication does, the pipeline documents and gates it. It cannot make the requirement disappear. That visibility is the point.

7Conclusion

Enforcement mandates fail quietly at the seam between the operating system's policy and the software a program actually runs. Closing that seam by hand does not scale. Closing it with denial-to-allow translation produces policies that are broad, unverified, and stale. Treating confinement as a build artifact changes the terms. The pipeline generates policy from behavior, verifies it adversarially under enforcement, routes privilege to a human gate, attests the result, and regenerates all of it on every release. Least privilege for legacy and vendor software becomes a property the pipeline proves. A reference implementation demonstrates the approach end to end on thirteen real applications, including proprietary products in every common input form. The remaining work is engineering, not research: verifier matrices across accredited baselines, disassembly for static binaries, and permissive-soak promotion telemetry.

AAppendix: an SELinux primer for this paper

This appendix covers the SELinux mechanics the body of the paper relies on, and nothing else. Readers fluent in type enforcement can skip it; readers new to SELinux should find that each concept below maps directly to a claim made earlier.

A.1 Labels: every process and file carries a context

SELinux attaches a security context to every process and every filesystem object. A context has four fields:

system_u : system_r : plex_t : s0
user role type level
Figure A-1. A security context. On the targeted policy that DoD baselines use, nearly all decisions turn on the third field — the type. This paper is exclusively about types.

A type attached to a process is called a domain (by convention something_t, e.g. plex_t). A type attached to a file describes what the file is to the policy: plex_exec_t (the application's executable), plex_var_lib_t (its state), etc_t (generic system configuration), shadow_t (the password hash database). You can see contexts with ls -Z and ps -Z. The paper's verification gate reads the running process's label directly (§2.2) because the label is ground truth, not inference.

A.2 Type enforcement: default deny, explicit allow

The kernel consults the loaded policy on every access: may a process in domain X perform permission P on an object of type Y and class C? Anything not explicitly allowed is denied. Rules read almost as sentences:

allow plex_t plex_var_lib_t:file { read write create unlink };
# processes in plex_t may read/write/create/delete files labeled plex_var_lib_t
Figure A-2. An allow rule. A least-privilege policy is the smallest set of such rules under which the application still works. The pipeline synthesizes that set (§2).

This is mandatory access control: it binds even root. A compromised application running as root in a well-confined domain still cannot read shadow_t or write etc_t unless the policy says so. The paper's static checks assert those rules are absent (§2.2). The same logic explains why granting a domain access to a broad shared type like var_log_t re-opens every other application's files carrying that label (§2.1).

A.3 The unconfined gap: why the mandate misses third-party software

The targeted policy ships domains for the distribution's own services (httpd_t, sshd_t, …). When the policy has never heard of a service, that service gets no domain of its own. systemd starts it, no transition rule fires, and it lands in a catch-all context such as unconfined_service_t, which the policy barely constrains. Enforcing mode is on; enforcement of that application is not. This is the entire gap the paper addresses (§1): the machine passes the STIG check while the vendor daemon runs with effectively no mandatory controls.

A.4 Domain transitions: how a process gets into its domain

Processes do not choose their domain; they acquire it at exec(). When systemd (init_t) executes a file labeled plex_exec_t, a transition rule in the policy moves the new process into plex_t:

init_t
systemd, starting the unit
exec →
plex_exec_t
label on the entrypoint binary
transition →
plex_t
the running, confined service
Figure A-3. The exec-time domain transition. The decision keys on the label of the resolved executable inode.

Three of the paper's failure classes (§4.1) live here. If the entrypoint is a symlink, the label that matters is the link's target — label the link and the transition never fires. If the entrypoint is mislabeled as ordinary content, init_t is denied execute and the service cannot start at all, while the app's own domain logs nothing (it never ran). And if a unit sets NoNewPrivileges=yes, the kernel permits only bounded transitions: the new domain must hold a subset of the old domain's permissions, which a fresh application domain never does. The kernel refuses the transition and the process silently stays in init_t. No allow rule fixes any of these. They are structural. The pipeline diagnoses them by name instead of generating more policy.

A.5 File contexts and restorecon: labels are state, policy is rules

A policy module carries file context mappings — regular expressions assigning types to paths (/var/lib/plexmediaserver(/.*)? → plex_var_lib_t). But mappings are only intent: labels live on the files themselves, applied at creation or by running restorecon. The two drift, and the distinction drives §2.1. When a file should carry the application's own type but carries a generic one, relabeling fixes it. An allow rule does not. Translating such denials into policy — audit2allow's failure mode — grants the domain access to every file on the system with that generic label. One more subtlety from §4.1: the distribution's own file contexts take precedence, and semodule rejects outright any module that re-declares a path expression the base policy already claims. The pipeline detects collisions before install.

A.6 Enforcing, permissive, and per-domain permissive

Globally, SELinux is either enforcing (denials are blocked) or permissive (denials are logged but allowed) — the latter being the notorious setenforce 0. More usefully for this work, a single domain can be made permissive while the rest of the system stays enforcing. The pipeline's observation rounds (§2, stage 3) run exactly this way: the application executes its workload unimpeded, every would-be denial is recorded, and nothing else on the system is weakened. Verification then removes the per-domain permissive flag and asserts it is gone. A permissive domain would pass any test.

A.7 AVC denials: the observation stream

Every denial (or in permissive mode, every would-be denial) is written to the audit log as an AVC record naming the source domain, target type, object class, and permissions:

type=AVC msg=audit(…): avc: denied { setgid } for pid=8113 comm="mosquitto"
scontext=system_u:system_r:mosquitto_t:s0 tcontext=system_u:system_r:mosquitto_t:s0
tclass=capability permissive=1
Figure A-4. An AVC record from corpus testing: mosquitto dropping root privileges needs the setgid capability. Classified as privileged, this became a review-gated rule (§2.1), not a silent grant.

These records are the raw material of the observe/refine loop. The pipeline never treats their absence as success by itself: §4.1's mislabeled-entrypoint case produces a perfectly clean log because the confined domain never ran. A refused transition surfaces as a separate SELINUX_ERR record, which the pipeline also parses.

A.8 Policy modules, ports, and the artifacts the pipeline ships

Policy is extensible at runtime. An administrator compiles a module from type-enforcement rules (.te) and file contexts (.fc) and loads it with semodule -i alongside the base policy, without rebuilding anything. Network ports are labeled the same way files are (a daemon needs permission to bind the port type, e.g. plex_port_t for 32400). The pipeline's deliverable (§3.2) is this module plus its labeling and port assignments, wrapped in an RPM whose install scripts load the module and run restorecon. A target system needs no SELinux expertise to consume it. The expertise lives in the factory. The enclave installs a package.
